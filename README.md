# Biographia Mobile — нативное приложение (React Native / Expo)

Мобильный клиент экосистемы SSOD/Dominex, продукт **Biographia** (веб-версия: `D:\projects\biographia`,
бэкенд на Flask, живёт на `biographia.ssod.pro`). Это отдельное нативное приложение, не веб-обёртка —
для веб-версии есть свой PWA-режим (см. `D:\projects\biographia\frontend`), это другая, более ранняя
работа над мобильным сценарием.

Документ рассчитан на то, что его прочитает либо человек, либо новый чат с Claude Code без памяти
предыдущих сессий — поэтому ничего не считается "само собой понятным".

---

## 1. Что это и зачем

Biographia — модуль «биографии» объектов/организаций/личных записей в экосистеме SSOD. Веб-версия
уже в проде. Пользователь никогда раньше не писал мобильных приложений и явно попросил: не просто
рабочий вариант, а архитектуру с расчётом на рост (новые экраны/функции добавляются, не переписывая
всё), код разбит по смыслу на файлы/папки, и побольше объяснений/комментариев — проект одновременно
рабочий и учебный.

Полный текущий архитектурный план — в файле плана Claude Code
(`C:\Users\asket\.claude\plans\steady-herding-treehouse.md` на машине разработки) и продублирован
здесь, в разделе 4, чтобы не потеряться при смене чата.

## 2. Окружение на этой машине — что установлено и как

Всё установлено **в этой же сессии** на конкретной Windows-машине разработчика. Если работа продолжается
на другой машине — весь этот раздел нужно повторить.

| Компонент | Версия/путь | Зачем |
|---|---|---|
| Node.js | через `winget install OpenJS.NodeJS.LTS` | среда выполнения JS/сборка |
| JDK | Eclipse Temurin 17, `C:\Program Files\Eclipse Adoptium\jdk-17.0.20.8-hotspot` | нужен Android-инструментарию (Java-based) |
| Android Studio | `C:\Program Files\Android\Android Studio` | источник SDK-компонентов; сама IDE не обязательна для работы через Expo/CLI |
| Android SDK | `%LOCALAPPDATA%\Android\Sdk` (`ANDROID_HOME`/`ANDROID_SDK_ROOT`, User env vars) | platform-tools (`adb`), platforms;android-34, build-tools;34.0.0, emulator, system-images;android-34;google_apis;x86_64 |
| AVD (виртуальный телефон) | `Pixel_biographia` (Android 14, `avdmanager list avd`) | эмулятор для тестирования без физического телефона |

**Переменные окружения (User scope, `[System.Environment]::SetEnvironmentVariable(..., "User")`):**
`JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, плюс в `PATH` добавлены
`%ANDROID_HOME%\cmdline-tools\latest\bin`, `%ANDROID_HOME%\platform-tools`, `%ANDROID_HOME%\emulator`.
Если открываете новую PowerShell-сессию для ручной работы — эти переменные там уже будут (User-scope
переменные подхватываются новыми процессами автоматически), но **фоновым командам, запущенным из
Claude Code в этой сессии, приходилось выставлять их вручную в начале каждой команды** — это
особенность инструмента, не системы.

### Известные грабли этой машины (если встретите те же симптомы — вот причина и фикс)

1. **Локальный прокси `127.0.0.1:2080`** прописан системно (реестр `HKCU\...\Internet Settings`,
   `ProxyEnable=1`) — влияет на WinINet-based инструменты (`winget`, `BITS`), обрывает большие
   закачки (>50-100 МБ) на середине. Обычный `curl` из Git Bash тоже иногда цепляет прокси. Рабочий
   обход: нативный `C:\Windows\System32\curl.exe` с флагом `--noproxy "*"` и `-C -` (докачка) —
   именно так качали и Android Studio (1.5 ГБ), и SDK cmdline-tools. Для sdkmanager (Java, свой сетевой
   стек) помогало явно снять `HTTP_PROXY`/`HTTPS_PROXY` из окружения перед вызовом.
2. **Ссылки на SDK-компоненты**: `edgedl.me.gvt1.com` — это CDN для самого установщика Android Studio,
   а НЕ для отдельных SDK-пакетов (command-line tools и т.п.) — те раздаются с `dl.google.com/android/repository/`.
   Перепутать домены легко (в том числе автоматический поиск по странице может ошибиться) — если 404,
   проверьте, что ссылка именно с `dl.google.com`.
3. **Эмулятор зависает сразу после `Windows Hypervisor Platform accelerator is operational`**
   (в логе `emulator -avd ... > log.txt` видно, что дальше строчки не появляются, CPU процесса
   qemu-system-x86_64 почти нулевой). На этой машине WHPX изначально был выключен (`Get-WindowsOptionalFeature
   -Online -FeatureName HypervisorPlatform` → `Disabled`) — включили (`Enable-WindowsOptionalFeature ...
   -All -NoRestart`), потребовалась перезагрузка. **После перезагрузки зависание всё равно
   повторялось** — вторая причина: Docker Desktop держит WSL2 (`docker-desktop` дистрибутив) постоянно
   запущенным в фоне, и это конфликтует с WHPX при выделении ресурсов гипервизора. Также на всякий
   случай добавлены исключения Windows Defender на `%LOCALAPPDATA%\Android` и `%USERPROFILE%\.android`
   (реальная типовая причина зависаний эмулятора на Windows — антивирус построчно сканирует
   мультигигабайтные файлы образов при каждом обращении). **Статус на момент написания: эмулятор
   ещё не подтверждён рабочим до конца** — это отдельная, не блокирующая задача (см. раздел 5).
   Тестирование пока идёт через физический телефон (Expo Go) и веб-режим.

## 3. Как запускать (после перезагрузки/новой сессии всё это нужно поднимать заново — ничего не переживает перезапуск ПК)

Из каталога `D:\projects\biographia-mobile`:

```powershell
# сначала убедиться, что PATH в текущей сессии видит Node/npm (User+Machine PATH)
$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")

# для физического телефона через Expo Go (тот же Wi-Fi, что и ПК)
npx expo start
# ссылка вида exp://<LAN-IP>:8081 - IP смотреть через Get-NetIPAddress (интерфейс "Беспроводная сеть")

# для быстрого предпросмотра в браузере на ПК (отдельный порт, чтобы не конфликтовать с первым)
npx expo start --web --port 8082
```

Порт 8081 разрешён во входящих правилах файрвола (`Expo Metro Bundler (8081)`) — телефон должен
достучаться без дополнительной настройки, если он в той же Wi-Fi-сети.

Для эмулятора (когда будет доподтверждён рабочим):
```powershell
$env:ANDROID_HOME = "$env:LOCALAPPDATA\Android\Sdk"
& "$env:ANDROID_HOME\emulator\emulator.exe" -avd Pixel_biographia
```

## 4. Архитектура (план, согласован с пользователем)

### Вход в приложение — новый токен-механизм на бэкенде Biographia

Веб-версия входит через браузерный SSO-редирект (cookie-сессия, `app/auth/routes.py` в
`D:\projects\biographia`). У мобильного приложения браузера в этом смысле нет. Решение: **Biographia
получает новый `POST /auth/mobile/login`** — принимает логин/пароль, проверяет их через Dominex
(`POST /api/v1/identity/credentials/verify`, уже существует и используется ssod_auth тем же образом —
Dominex единственное хранилище паролей в экосистеме), выдаёт собственный долгоживущий токен, хранит
его хеш (не сырой токен) в новой таблице `DeviceSession`. Дальше все обычные вызовы (`/records`,
`/entities`, ...) принимают `Authorization: Bearer <токен>` наравне с cookie-сессией — бизнес-логика
роутов не дублируется и не переписывается, только точка входа в `require_session()`
(`app/core/auth.py`) расширяется.

Это ровно тот механизм («Biographia выпускает собственный device-токен»), что уже описан в
`biographia_tz.md` §4.1 у веб-проекта — просто без QR-привязки (Step 1 оттуда), которую можно
добавить позже как более удобный способ получить тот же токен, не меняя сам механизм.

### Технологии

- **TypeScript** с первого дня (не JS с миграцией потом).
- **Expo Router** — файловая маршрутизация (экран = файл в `app/`), текущий стандарт для новых
  Expo-проектов, вместо одного `App.js`.
- **`StyleSheet.create`** (встроено в React Native) для стилей — без сторонних библиотек стилизации
  на старте.

### Структура папок

```
biographia-mobile/
  app/                # Expo Router: экран = файл. Только экраны/навигация, без бизнес-логики.
    _layout.tsx        # корневой layout: проверка токена, тема
    (auth)/login.tsx    # экран входа
    (tabs)/              # нижние вкладки, зеркалит sidebar/tab-bar веб-версии
      _layout.tsx
      index.tsx           # "Вики" - лента записей
      diary.tsx            # личный дневник
      profile.tsx           # личный кабинет
    entity/[kind]/[id].tsx  # карточка сущности, те же kind/id что и веб-роут /entity/:kind/:id
  src/
    api/               # HTTP-слой, зеркалит frontend/src/api.js по духу, но с Bearer-токеном
      client.ts          # один fetch-хелпер + подстановка Authorization header
      auth.ts              # login()/logout(), хранение токена
      records.ts             # по одной функции на маршрут
      entities.ts
    components/        # переиспользуемые кусочки UI (RecordCard и т.п.)
    features/          # логика по смыслу (не по типу файла): records/, diary/, auth/ - каждая
                        # со своими компонентами/хуками
    context/           # AuthContext - аналог ViewerContext.jsx у веба
    theme/              # цвета/отступы именованными константами, перенесены из main.css веб-версии
                        # (--accent/--bg-sidebar/--success/...), чтобы визуальный язык совпадал
    utils/              # общие мелочи (форматирование дат и т.п.)
  assets/
```

### Осознанно отложено (не в первом заходе)

- QR-привязка устройства из ТЗ §4.1 — токен-вход по паролю замещает её как более простой первый способ.
- Личные (зашифрованные) записи/вложения на мобильном — на веб-стороне это тоже не до конца
  реализовано (личные вложения вообще не поддержаны бэкендом), крипто-часть (`masterKey.ts`)
  переносить в RN — отдельная задача после того как заработает основной CRUD-поток.
- Полноценный офлайн (как в веб-PWA, `frontend/src/offline/queue.js`) — сначала рабочий онлайн-поток.
